> been done: it is pending the W1b-1 deploy (there is no live control plane or stamp to
> walk against). Per `ux-baseline.md` this surface is therefore **unverified**,

| Control | Calls | Backend |
|---|---|---|

| Retry | `POST /api/health/tenants/[id]` `{retry:true}` | control plane `POST /jobs/{id}/retry` |
| Tenant list | `GET /api/health/tenants` | control plane `GET /tenants` |
| Prerequisites list + Fix it | `GET /api/admin/gates`, then the gate wizard (`/api/admin/gates/[id]/options`, `/resolve`) | gate registry; admin-scoped, hidden for non-admins |
| Save quotas | `PATCH /api/health/tenants/[id]` `{quotas}` | control plane `PATCH /tenants/{id}` |
| Apps tab list | `GET /api/health/tenants/[id]/apps` | control plane `GET /api/health/auth/clients` (filtered to this tenant's app and backend clients; inline keys reduced to count + kids) |
| Register app / backend service | `POST /api/health/tenants/[id]/apps` | control plane `POST /api/health/auth/clients` (tenant = the item's binding, never the body; `clientType`, `roleIds`, `introspect`, and exactly one of `jwksUrl` / `jwks`) |
| Disable / Enable, Edit launch URL | `PATCH /api/health/tenants/[id]/apps/[clientId]` | control plane `PATCH /api/health/auth/clients/{id}`, after checking the client belongs to this tenant |
| Launch | `POST /api/health/tenants/[id]/apps/[clientId]/launch` `{patient?}` | control plane `POST /api/health/auth/launch` with the **session** oid; `iss` comes from the CP reply |
| Patient search (launch dialog) | `POST /api/health/tenants/[id]/apps/patient-search` `{q, birthdate?}` | control plane `POST /api/health/auth/tenants/{t}/patient-search` with the session oid; `{unavailable}` and `{notPermitted}` are rendered, never rows |

Authorization: listing, launching and searching need Reader on `health.tenant-admin`. Registering and patching need
Contributor. A launch or search acts as the signed-in user, whose own FHIR roles bound what the token can reach.

The control plane's `tenant.create` job deploys the tenant's PostgreSQL database,
two Blob accounts, an Event Hubs hub, a managed identity, a capacity alert and
Key Vault keys on the stamp, then reads each back; the Console renders those
receipts and never calls ARM for a tenant itself.

## auto-bind behaviour

- Names: the control-plane tenant carries the item's display name verbatim; its
  id is a lowercase slug (2-30 chars) recorded on the item with a `sanitized`
  flag. A slug owned by a different tenant gets an item-id suffix.
- Self-heal: each open re-reads the tenant. A tenant removed from the control
  plane is re-registered; a lost state write is re-derived and the existing
  tenant adopted; a bound tenant is re-verified by an idempotent job once per 24 h.
- Never a bind form: provisioning progress renders on the Overview.
- Create-time: `healthTenantAutoBindOnCreate` (`lib/azure/auto-bind.ts`, called from `autoBindOnCreate`) provisions
  and binds on create; covered by `lib/azure/__tests__/auto-bind-health-tenant.test.ts` (one tenant, one job, name verbatim).
  First open adopts that binding instead of duplicating it.
- The Overview is a `SplitPane` (storage key `health-tenant-overview`) from 1100px wide, stacked below that. The layout
  is untested in a real browser (G1 pending).

## Capability (D12)

`health.tenant-admin` ("Health Tenant Admin") is NOT inherited from Loom
administration. Decision D12 in
`PRPs/active/loom-health-data-services/RISKS-AND-OPEN-DECISIONS.md` resolves it as
"New `Health Tenant Admin` capability, not inherited from Loom Admin" (the
rejected alternative is "inherit"). The shared `checkCapability` returns allow for
every Loom tenant admin and walks ancestor grants, so health does not use it: the
routes and the provisioner use `app/api/health/tenants/_lib/tenant-admin-gate.ts`,
which admits only an explicit grant on `health.tenant-admin` itself. A Loom tenant
admin can still grant themselves the capability at `/admin/permissions`; the grant
is deliberate and auditable instead of implied. Device-code sessions are refused.

## Not done in this change

- The in-browser walk (G1) has not been run (pending the W1b-1 deploy); this is not A-grade.
- The Apps tab (#5454 A6) has not had a G1 walk either. It is proven only against a faked BFF
  (`lib/editors/health/__tests__/smart-apps-tab.test.tsx`) and faked CP client methods
  (`app/api/health/tenants/__tests__/smart-apps-routes.test.ts`). The console session oid must be in the same Entra
  tenant the authorization server federates to, or the launch handle will not match the app's sign-in.
- Backend-service and inline-JWKS registration (#5151) has no G1 walk and no live CP receipt; it is proven against
  faked CP client methods only. Until CP #5515 merges, the CP on main refuses `introspect` (strict schema), so a
  registration with the switch on gets the CP's 400; with the switch off the field is not sent.
- The backend role list is mirrored from `apps/loom-health-cp/src/auth/role-scope-map.v1.json` (the Console image
  cannot import CP source and the CP exposes no role-list endpoint). `lib/health/__tests__/smart-registration.test.ts`
  reads the CP file and fails on drift.
