# Parity matrix — Programmability & extensibility

**Parent:** [`PRP.md`](./PRP.md) · Domain key `programmability` · Measured **2026-08-24** · **51 rows**

Every Snowflake programmability/extensibility capability, what Loom has today, the target
Azure-native/OSS architecture, a verdict per sovereign boundary, effort, and — the column that
matters most — the **semantic delta** a migrating user hits on day one.

## Binding operator decisions this matrix is written under (2026-08-24)

1. **Migration-first.** Loom is the destination. The Snowflake MCP/REST connector exists to read
   an existing account and get data and definitions *out*. A research lane recommended
   coexistence; that recommendation is **overruled** and the sequencing below reflects it —
   inventory/assessment/transpile rows come before interop rows.
2. **Transpiler now, wire-compatible later.** Offline conversion (Snowflake SQL, dbt, DDL, stored
   procedures → Loom engines) ships first. A Snowflake-wire-compatible endpoint is a later wave.
3. **Outcome parity, differences documented.** Match what a user can exercise and observe, using
   the best Azure/OSS mechanism underneath. Mechanism parity was **rejected**. Every genuine
   semantic difference is named in the last column so a migrating user meets it in a doc.

## How to read this

- **Loom today** — `Built` (real backend, works) · `Partial` (substrate exists, missing the user
  surface / a language arm / the Gov path) · `Missing` · `Cannot match` (no Azure/OSS equivalent
  for the headline capability — the row says so instead of inventing a design).
- **Boundary verdicts** — ✅ same capability, same mechanism · ⚠️ degraded or different path
  (**the substitute is named, never left blank**) · ❌ not achievable.
- **Two boundary facts govern every verdict in this file** (verified 2026-08-24):
  - **Azure Government does not offer Databricks SQL or Unity Catalog.** Any design whose
    Commercial mechanism is a Databricks SQL/UC call is **Synapse Spark, Trino, or `apps/loom-unity`
    in GCC-High/IL5/DoD** — never a Databricks call. Rows below that carried a Databricks-in-Gov
    claim in research are corrected here.
  - **There is no `dod.bicepparam`.** `platform/fiab/bicep/params/` holds `commercial-full`,
    `commercial`, `gcc`, `gcc-high`, `il5`, `dlz-attach`, `tenant-dmlz` — and nothing for DoD. So
    every DoD verdict in this file is **design-viable, undeployed**: it states what the boundary
    *can* support, not what has ever run there. Per `deploy-integrity.md` R4 that is an untested
    path and is declared untested. **DoD ✅ in this file never means "verified".**
  - GCC runs on Azure Commercial infrastructure, so its verdict tracks Commercial except where a
    compliance overlay (not an Azure service gap) bites. GCC-High and IL5 are Azure Government
    (`USGov Virginia / Arizona / Texas`), where `containerPlatform = 'containerApps'` is GA and
    asserted in both params files.
- **Effort** — S (days) · M (1–2 weeks) · L (2–4 weeks) · XL (4+ weeks).

### The four rows that are genuinely unmatched, stated plainly

1. **SQL-callable Python UDAF (13)** — SQLCLR is absent from Azure SQL Database and Synapse
   dedicated SQL pools, so there is no `CREATE AGGREGATE` path for a Python aggregate in any cloud.
   Spark `GROUPED_AGG` is a real aggregate but a **topology change**. Equally bounded in every
   boundary, so this is not a cloud-parity gap.
2. **In-engine memoization (15)** — no `MEMOIZABLE` attribute exists on Azure SQL or Synapse. Loom
   can cache at the HTTP invoke boundary; a T-SQL scalar function inside a warehouse query gets
   nothing, and that query pattern must be rewritten.
3. **Payment collection in sovereign boundaries (40)** — metering, dimensions, price sheets and
   per-consumer statements all work everywhere; **transactable marketplace collection does not exist
   in Azure Government**. Microsoft's boundary, not Loom's, but a package depending on it must
   declare Commercial-only availability or it breaks at install in Gov.
4. **Snowpark-optimized warehouse (47)** — the Loom `warehouse` item has **no Python execution mode
   at all**, so there is nothing to resize. Memory-optimized handler compute exists (E-series ACA,
   Synapse `nodeSizeFamily=MemoryOptimized`) but reaching it is a topology change.
