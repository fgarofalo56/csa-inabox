# Parity matrix — AI, ML & Cortex

**Parent:** [`PRP.md`](./PRP.md) · Domain key `ai` · Measured against the tree at
`9a888b58d6` on **2026-08-24** · **41 rows**

Every Snowflake AI/ML/Cortex capability, what Loom has today (re-verified against the
current tree, not the research snapshot), the target Azure-native/OSS architecture, the
five per-boundary verdicts, effort, and — the column that matters most — the **semantic
delta** a migrating user hits on day one.

## How to read this

- **Loom today** — `Built` (real backend, works today) · `Partial` (mechanism exists;
  missing the SQL surface / UI / Gov path / one half of the fusion) · `Missing` ·
  `Cannot match` (named gap, no design offered — see the delta column for why).
- **Boundaries** — ✅ same capability · ⚠️ achievable via a **named substitute**, behaviour
  differs · ❌ not achievable. Per `cloud-parity.md` a blank is not allowed: every ⚠️ names
  its substitute inline or in the delta column.
- **The Databricks rule.** Azure Government (GCC-High / IL5 / DoD) supports **neither
  Databricks SQL nor Unity Catalog**. Loom's *current* AI-function path pushes down to
  Databricks `ai_*` builtins (`DBX_BUILTIN_OPS`, `ai-enrichment-client.ts:65`), so **today's
  in-database AI SQL is Commercial/GCC-only**. Every row below that claims a sovereign
  verdict does so through the AOAI-orchestrated path, an OSS engine container, or a named
  Azure service — never through Databricks. The repo's own convention (`knowledgeGovGate()`
  gates GCC-High + DoD, not Commercial + GCC) is followed here: **Commercial and GCC run on
  Azure Commercial regions; GCC-High, IL5 and DoD run on Azure Government.**
- **Posture.** Per the binding operator decisions of 2026-08-24 this domain is
  **migration-first**: the MCP connector reads a customer's Snowflake account to extract
  data and definitions; it is not a coexistence substrate. SQL surfaces below are
  **transpiler-first** — an offline converter lands before any wire-compatible endpoint.
  Parity depth is **outcome parity with documented differences**, never mechanism parity.
- **Effort** — S (days) · M (1–2 weeks) · L (2–4 weeks) · XL (4+ weeks).

## 9. Cross-cutting findings

Three things recur across enough rows to be program-level rather than per-row.

**The SQL-engine bypass is the single biggest structural risk in this domain.** Rows 2, 3,
4, 7, 8, 9, 10 and 13 all add functions that call AOAI or AI Search from inside
`loom-trino` / `loom-duckdb`. Those containers do not import `lib/copilot/token-budget.ts`
and do not pass through `resolveAoaiTarget`. Unless the engines are structurally unable to
obtain a model token without a Loom policy/budget check, rows 16, 21, 33 and 34 are all
decorative for anyone who can write SQL. This should be built **first**, before the first
UDF ships — retrofitting a chokepoint after eight functions exist is how it ends up
conventionally called instead of structurally required.

**Databricks is not a Gov answer and the current AI-function path depends on it.** Today's
in-database AI SQL pushes down to Databricks `ai_*` builtins
(`ai-enrichment-client.ts:65`), which do not exist in Azure Government. The AOAI-orchestrated
`runAoaiEnrichment` is the portable fallback, and the Trino/DuckDB `loom-aisql` module is the
durable one. Every row above treats Databricks push-down as a **Commercial/GCC accelerator**,
never as the default — that inversion is what makes the sovereign verdicts hold.

**There is no GPU node pool anywhere in `platform/fiab/bicep`.** Rows 5, 11 and (at scale)
40 all assume one or accept a CPU throughput ceiling. Adding an AKS GPU pool breaks the
~$0-idle property that `loom-trino` and `loom-duckdb` established, so this is a deliberate
cost/capability decision that should be made once, explicitly, rather than three times
inside three rows.
