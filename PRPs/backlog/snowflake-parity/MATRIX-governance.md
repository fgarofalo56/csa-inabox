# Parity matrix — Governance & data quality

**Parent:** [`PRP.md`](./PRP.md) · Measured 2026-08-24 against `9a888b58d6` · **36 rows**

Every Snowflake Horizon governance and data-quality capability, what Loom has today, the
target Azure-native/OSS architecture, a **per-boundary** verdict, effort, and — the column
that matters most — the **semantic delta** a migrating user hits on day one.

Posture is **migration-first** (PRP §1 operator decision 1): Loom is the destination.
Parity depth is **outcome parity with differences documented** (decision 3) — we match what a
user can exercise and observe, using the best Azure/OSS mechanism underneath, and we NAME
every place the semantics diverge. Mechanism parity was explicitly rejected.

## How to read this

- **Loom today** — `Built` (real backend, works) · `Partial` (mechanism exists; missing a
  dimension, a surface, or the Gov path) · `Missing` · `Cannot match` (named limit, no
  invented design).
- **Boundaries** — ✅ same capability · ⚠️ degraded/different path, **substitute named in the
  cell** · ❌ not achievable. Per `cloud-parity.md` a blank is not allowed.
- **Effort** — S (days) · M (1–2 weeks) · L (2–4 weeks) · XL (4+ weeks).
- **Evidence** — `file:symbol`, or the search that found nothing. Every claim below was
  re-grepped at authoring time, not carried from research.

## Corrections to the research pass (verified against the tree and against Snowflake's docs)

The research ran hours before this matrix. Six of its claims did not survive re-checking. Each
is corrected in the row that carries it.

| # | Research claimed | Verified truth | Row |
|---:|---|---|---|
| **C1** | Snowflake aggregation policies allow `COUNT/SUM/AVG/MIN/MAX/APPROX_COUNT_DISTINCT`, and a below-threshold group is suppressed | **Only `AVG`, `COUNT` (incl. `COUNT DISTINCT`), `HLL`, `SUM` are permitted** — `MIN`/`MAX` are *not*, because they leak a single value. And a small group is **not suppressed**: Snowflake folds it into a **remainder group with a NULL `GROUP BY` key**, so totals still reconcile. The proposed `HAVING COUNT(*) >= N` view **drops** those rows and silently changes every total. ([docs](https://docs.snowflake.com/en/user-guide/aggregation-policies)) | 5 |
| **C2** | A projection policy must also deny `GROUP BY`/`ORDER BY`/`DISTINCT`, or "the ban is trivially bypassed" | **Backwards.** Snowflake *explicitly permits* the column in `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY` and inner queries, documents that values *can be inferred*, and says the feature is "best suited for use with partners and customers with whom you have an existing level of trust." Hardening it would make Loom **stricter than Snowflake** and break queries that work today — a migration regression, not a fix. ([docs](https://docs.snowflake.com/en/user-guide/projection-policies)) | 6 |
| **C3** | Join policies have a `mode: 'required' \| 'forbidden'` with a `withTables[]` list; and Snowflake can be defeated by laundering a join through a user-created view | **Wrong shape and wrong weakness.** The object is `JOIN_CONSTRAINT(JOIN_REQUIRED => TRUE)` + `ALLOWED JOIN KEYS (col…)` — there is **no join-forbidden mode**. And **a regular view over a join-constrained table is itself protected**, so the "launder one level down" attack does not work in Snowflake. It *does* work against a Loom secure-view emulation — the delta is the reverse of what was written. ([docs](https://docs.snowflake.com/en/user-guide/join-policies)) | 7 |
| **C4** | "Schema-level DMF association" is a Snowflake capability Loom lacks | **No such capability.** Snowflake DMFs attach to **individual tables or views** — "associate a DMF with a table or view". A DMF is a *schema-level object* (reusable, lives in a schema); that is not a schema-level *association*. The real gap is that Loom's `DqRule` is a per-scope row, **not a reusable named function** applied to N tables. Loom's proposed scope grammar would **exceed** Snowflake, and should be sold as such. ([docs](https://docs.snowflake.com/en/user-guide/data-quality-working)) | 20 |
| **C5** | `LOOM_LAKE_ACCOUNT` is empty, so credential vending has nothing to vend | **The bind exists in IaC** — `iceberg-catalog-aca.bicep:182`, `duckdb-aca.bicep:147`, `loom-risingwave-aca.bicep:288`, all unconditional. The parity doc's "EMPTY on both" is a **live-estate observation from 2026-08-07**, i.e. a `deploy-integrity.md` R3 drift finding, **not a missing bicep module**. Fixing it is a deploy verification, not a build. | 27 |
| **C6** | Azure Budgets must be built for tag-scoped resource monitors; and DQ findings have no action-item lifecycle | Both understate what exists. **Budgets CRUD is already real** — `budgets-client.ts:upsertBudget/buildBudgetBody/budgetScope`, gate `svc-budgets-write`, granted by `cost-management-reader-rbac.bicep`; the narrow gap is that `BudgetInput` has **no tag filter** and notifies `contactEmails` rather than an action group. **DQ findings already have a lifecycle** — `DqFindingStatus = 'open' \| 'acknowledged' \| 'resolved' \| 'muted'` — and `app/admin/incident-console` + `lib/observability/incident-*` already own triage and assignment. | 11, 22 |

Two smaller notes carried into rows: `remediateRecommendation()` already PUTs a real
`Microsoft.PolicyInsights/remediations` task (so Trust Center does **not** start read-only),
and `apps/loom-trino/etc/` contains only `config/jvm/log/node.properties` — **no event
listener is configured**, so the column-grain query source the research treated as an owned
asset is a design, not a deployed one.
