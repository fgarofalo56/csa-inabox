# MATRIX-security — Snowflake → CSA Loom capability parity: Security & identity

**Domain key:** `security` · **Written:** 2026-08-24 · **Verified against:** `main` @ `9a888b58d6`

## Binding operator decisions this matrix is written under (2026-08-24)

1. **MIGRATION-FIRST.** Loom is the destination. The MCP connector's job in this domain is to
   **read the customer's existing Snowflake account out** — the role graph (`SHOW ROLES`,
   `SHOW GRANTS`), users and user types, network policies, password/session/authentication
   policies, and the security-integration list — so it can be re-expressed as Loom objects.
   Interop is the means; coexistence is not the end state. A research lane recommended
   coexistence for the catalog layer; **that recommendation is overruled** and the sequencing
   below puts the importer ahead of any bidirectional-sync work.
2. **TRANSPILER NOW, WIRE-COMPATIBLE LATER.** Snowflake security DDL (`CREATE ROLE`,
   `GRANT … TO ROLE`, `GRANT … ON FUTURE`, `CREATE NETWORK POLICY`, `CREATE NETWORK RULE`,
   `CREATE PASSWORD POLICY`, `CREATE SESSION POLICY`, `CREATE AUTHENTICATION POLICY`,
   `ALTER USER … SET RSA_PUBLIC_KEY`) is converted **offline** into Loom role-plane /
   policy-plane objects. A Snowflake-wire-compatible endpoint is a later wave.
3. **OUTCOME PARITY, DIFFERENCES DOCUMENTED.** Match what a user can exercise and observe.
   Mechanism parity (replicating Snowflake's own key hierarchy, Snowgrid replication
   internals, vendor-side MPA) is explicitly rejected. The last column is where that debt
   is paid — read it as the deliverable, not the caveat.

**Standing sovereign substitutions used throughout, established once here:**

- **Databricks Unity Catalog and Databricks SQL do not exist in Azure Government.** Every
  catalog-grant projection in this matrix therefore targets **`apps/loom-unity`** (the LF AI &
  Data OSS Unity Catalog server + Loom's v0.5.1 server overlay) in GCC-High / IL5 / DoD.
  loom-unity is already Loom's **default** backend per `no-fabric-dependency.md`, so this is a
  Gov-strength case, not a Gov gap. No row below claims Gov viability via a Databricks call.
- **Azure Front Door Premium** is constrained in sovereign boundaries → **Application Gateway
  WAF v2**, already deployed by `platform/fiab/bicep/modules/admin-plane/app-gateway.bicep`.
- **Azure Managed HSM** availability is region-limited inside Gov → **Key Vault Premium**
  (HSM-backed, FIPS 140-2 Level 3). The surface must report which one it actually got.
- **The public GitHub Actions OIDC issuer** (`token.actions.githubusercontent.com`) is
  unreachable from an air-gapped boundary → **GitHub Enterprise Server**, **Azure DevOps
  Server**, or the in-boundary Container Apps self-hosted runner Loom already operates for Gov
  verification.
- **Azure service-tag *content* is per-cloud** (`AzureCloud.usgovvirginia` ≠ `AzureCloud`). A
  rule authored against a Commercial tag matches nothing in Gov.

## Domain roll-up

**41 capabilities. Zero are at parity today.** That is the headline and it is not softened
anywhere above: not one row in Security & identity is `built`. Seventeen are `partial`
(a real, often well-engineered substrate exists but the Snowflake-visible capability does
not), twenty-three are `missing`, and one — **instance roles / Snowflake classes** — is a
named `cannot-match` where the honest answer is a documented concept mapping onto app
instances, not an invented abstraction.

Three additional **cannot-match** properties sit inside otherwise-buildable rows and are
called out in their own semantic-delta cells rather than being smoothed into a design:

1. **Periodic rekeying cannot be transparent.** Snowflake rekeys yearly with no data
   movement the customer sees. Loom's lake rekey is a full transactional rewrite with real
   compute cost and changed file mtimes.
2. **Multi-party approval cannot have a vendor as the second party.** Snowflake's MPA
   resists a fully compromised customer tenant precisely because Snowflake is outside it.
   Every approver Loom can name is inside the customer's tenant.
3. **Organizations cannot span sovereign boundaries.** A Commercial org and a GCC-High org
   are separate organizations with separate directories, and Entra cross-cloud B2B is not a
   sound basis for an authorization plane.

**The single highest-leverage correction in this document** is #6: `conditional-access.bicep:10-12`
asserts that service principals cannot create Conditional Access policies. That is false —
verified against live Microsoft Learn, `POST /v1.0/identity/conditionalAccess/policies`
supports Application permissions and is available in Global, US Gov L4 and US Gov L5 (DoD).
That one stale comment is why **five rows** (network policies, network policy precedence,
authentication policies, MFA, and half of session policies) currently read as impossible.
Deleting it is in scope for the first PR that touches this family, not a follow-up.

**Ordering implied by MIGRATION-FIRST.** The role plane (rows 1–4) and the Snowflake
`SHOW ROLES` / `SHOW GRANTS` importer come first, because nothing else in this domain has a
principal model to attach to. The Conditional-Access family (network + authentication + MFA
+ session) comes second, because it is unblocked by a comment deletion and is the largest
cluster of `missing` rows sharing one mechanism. Keycloak (SAML broker, multi-IdP, and the
authorization server) is one XL component serving three rows and should be sequenced as one
decision, not three.
