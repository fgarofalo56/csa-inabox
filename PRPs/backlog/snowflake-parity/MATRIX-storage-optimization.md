| 1 | **Micro-partitions** | Missing as an inspectable concept. `lib/azure/delta-history.ts` already reads `_delta_log` commit JSON over ADLS **with no SQL engine** — but parses only the `commitInfo` action | Extend that proven pattern into `delta-file-stats.ts`: parse `add`/`remove` actions for `path`, `size`, `modificationTime`, `partitionValues`, `deletionVector` and the `stats` JSON (`numRecords`, `minValues`, `maxValues`, `nullCount`). Predicted and measured **will disagree** (runtime filters, dynamic partition pruning, deletion vectors); show both and explain the gap, never reconcile silently. Trino query telemetry is in-memory by default and disappears on container recycle unless the event listener is wired to Log Analytics. |
| 3 | **`SYSTEM$CLUSTERING_DEPTH` / `SYSTEM$CLUSTERING_INFORMATION`** | Missing | **Computable exactly, not approximated.** Sort per-file min/max intervals by lower bound, sweep to build an overlap-depth histogram, emit `total_partition_count`, `average_overlaps`, `average_depth`, `partition_depth_histogram`, `clustering_key` — **deliberately mirroring Snowflake's own JSON key names** so a migrated dashboard or script maps 1:1. Serving a `SYSTEM$`-named function invites assuming full Snowflake semantics: **reject unsupported argument shapes explicitly** (PRP §12-7). |

## 2. Automatic maintenance — Snowflake Optima (5 rows)

All five are arms of one **Loom Autotune** ACA cron Job (W6.3), following the proven
`asset-reconciler-job` / `lineage-extractor-job` / `cost-anomaly-monitor-job` pattern and
writing to the existing `maintenance-jobs` Cosmos container.

| # | Snowflake capability | Loom today | Target architecture | Gov | Effort | W | Semantic delta / risk |
|---:|---|---|---|:--:|:--:|---|---|
| 4 | **Automatic Clustering** | Partial in name only — `LakehouseSettingsDoc.deltaDefaults.autoOptimize` is a **persisted preference**, not enrollment; nothing runs | Autotune's clustering arm: read `clustering-info` per enrolled table, compare `average_depth` to a per-table target, submit `OPTIMIZE … ZORDER BY` or Delta liquid `CLUSTER BY` + `OPTIMIZE` through the **existing** `/api/lakehouse/maintenance` Livy path. Also set `delta.autoOptimize.optimizeWrite` + `autoCompact` so the **write** path compacts inline | ✅ default path is Synapse Spark via Livy (all Gov boundaries); ACA Jobs are in Azure Government; Databricks stays an opt-in alternative. **Snowflake Automatic Clustering is unavailable to IL5/air-gapped customers entirely** | L | W6.3 | Snowflake's is a **continuous, credit-metered background service with no user-visible schedule**; Loom's is a cron-bounded batch (default 30 min) with an explicit compute budget, so **worst-case staleness equals the tick**. Delta **liquid clustering is incremental** and semantically much closer than Z-order, which rewrites the whole selected set. **Runaway cost is the primary risk** — a naive depth target can rewrite terabytes nightly: hard per-tenant budget, dry-run preview, cost attribution into the FOCUS mart. **MUST no-op when the estate is PAUSED** — a job that resumes Spark pools silently reverses a deliberate pause. Concurrent `OPTIMIZE` and user writes produce Delta commit conflicts: bounded retry, **fail closed**, never a half-compacted table. |
| 5 | **Optima Clustering vs Clustering Classic** | Missing the inferred tier; the declared tier is what row 4 builds | `autoClustering.mode: 'declared' \| 'inferred'` on the same config. Inferred ranks candidates by **observed predicate frequency × selectivity × current depth**, top-k ≤ 4, from the row-2 telemetry store | ✅ inference runs on Loom-owned telemetry and Loom-owned metadata | L | W6.4 | **A place Loom can exceed rather than match:** the choice is shown **with its evidence** — *"chosen because 71% of scans in the last 14 days filter on `order_date`, current depth 12.4"* — which Snowflake does not do. Risks: sparse or unrepresentative telemetry picks the wrong columns and pays for a full rewrite (minimum-observation threshold + **mandatory** dry-run before the first inferred run); predicate frequency is **biased by what already runs well**, so the feedback loop can entrench a bad layout; and flapping between inferred sets would rewrite continuously — hysteresis and a minimum dwell time. |
| 6 | **Optima Indexing** | Missing | Autotune's indexing arm, three real mechanisms: (i) Delta **bloom-filter** indexes — `CREATE BLOOMFILTER INDEX` on Databricks, `delta.bloomFilter.*` table properties on Delta OSS/Synapse Spark; (ii) **widen `delta.dataSkippingStatsColumns`** then re-run `OPTIMIZE` so min/max actually exist for the columns users filter on; (iii) Iceberg column stats / Puffin sketches via `rewrite_data_files` | ✅ via Synapse Spark + Delta OSS table properties. The Databricks `CREATE BLOOMFILTER INDEX` syntax is Commercial-only and is the opt-in alternative | L | W6.3 | **This is probabilistic file-level skipping, not a secondary index** — a point lookup gets dramatically fewer files scanned, but it does **not** become an O(1) seek the way "Optima Indexing" implies. Where true point-lookup latency is required, escalate to the serving-tier projection rather than overpromising. Bloom support varies by Delta/Spark runtime on Synapse pools: **probe and report "not supported on this runtime" with the exact upgrade action** — a silent no-op is a vaporware violation. Widening stats columns requires **rewriting files**, i.e. the cost of a full `OPTIMIZE`, which users will not expect from an "indexing" feature. |
| 7 | **Optima Metadata** | Missing — every storage/clustering/table surface re-walks `_delta_log` on demand | Autotune's metadata arm materializes per-table summaries (file count, byte totals by class, per-column min/max, row counts, clustering depth, last commit version) into a new Cosmos `table-metadata-cache`, refreshed **incrementally** by reading only commits after the cached version — cheap and exact, because the log is append-only. For large estates the same summaries also land as Delta/Parquet on ADLS so Trino/DuckDB can query them as a system view | ✅ Cosmos + ADLS + ACA in every boundary; derived entirely from customer-owned storage, which is precisely why it survives an air-gapped enclave | M | W6.3 | **Honestly scoped:** this accelerates **Loom's** metadata surfaces, not the engines' planners — do not claim otherwise. **A stale cache presented as current is the classic silent-wrong-number failure:** `asOfVersion` + staleness are **non-optional** in every consuming surface, not a tooltip. Cosmos RU scales with table count on wide estates (batch + a bytes/RU budget, with the ADLS materialization as the escape hatch). Incremental refresh must handle log truncation and checkpoint-only history, or the cache silently diverges after a `VACUUM`. |
| 8 | **Optima Planning** | Partial — `lib/azure/statistics-client.ts` exists but is **on-demand only** (a button a user must remember): `ANALYZE TABLE … COMPUTE STATISTICS FOR ALL COLUMNS` on Databricks, `CREATE/UPDATE STATISTICS` on Synapse | **Be explicit: Loom does not replace the backing engines' optimizers, so there is no honest 1:1.** Two real deliverables instead — (1) Autotune's statistics arm, triggered by staleness computed from `_delta_log` commit metrics (rows changed since last `ANALYZE`); (2) a per-engine plan viewer (Trino `EXPLAIN [ANALYZE]`, Spark `EXPLAIN FORMATTED`, Synapse `SET SHOWPLAN_XML` / `sys.dm_exec_query_plan`) annotated with row-2 pruning counters, plus a **plan-regression signal** diffing plan shape for the same statement hash across runs | ✅ | M | W6.3 | Render plans **per engine, never falsely unified** — three optimizers, three plan languages. The plan-regression diff is the operationally useful part of "planning" that Loom can genuinely own. Claiming a proprietary planning service equivalent would be vaporware. |
