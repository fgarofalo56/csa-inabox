# Parity matrix — Snowsight UI surfaces

**Parent:** [`PRP.md`](./PRP.md) · Domain key `ui` · Measured against the working tree **2026-08-24** · **40 rows**

Every Snowsight UI surface, what Loom has today (re-verified against the tree, not the
research snapshot), the target Azure-native/OSS architecture, a per-boundary verdict, effort,
and — the column that matters most — the **semantic delta** a migrating user hits on day one.

## How to read this

- **Loom today** — `Built` (real backend, real surface, works) · `Partial` (mechanism exists;
  missing the object, the aggregation, the Gov path, or the surface) · `Missing` ·
  `Cannot match` (no design ships; the gap is named instead).
- **Boundaries** — ✅ same capability · ⚠️ different path, **substitute named** · ❌ not
  achievable in that boundary. Per `cloud-parity.md` a blank is not permitted.
- **Effort** — S (days) · M (1–2 weeks) · L (2–4 weeks) · XL (4+ weeks).
- **⛔** in the semantic-delta column marks a *named cannot-match component* — the row ships a
  design, but one dimension of the Snowflake capability is genuinely unreproducible and is
  stated rather than papered over.

### Binding posture applied to every row

Per the operator decisions of 2026-08-24:

1. **Migration-first.** Loom is the destination. Rows that could have been written as
   coexistence surfaces (the account selector, linked catalogs, Partner Connect) are written as
   *get-them-off-Snowflake* surfaces. The research lane's coexistence recommendation is
   overruled; where a row diverges from its research design for this reason it says so.
2. **Transpiler now, wire-compatible later.** Row 12 (worksheet migration) leans on the
   existing `lib/migrate/sql-transpile.ts` offline path. No row assumes a Snowflake-wire
   endpoint exists.
3. **Outcome parity, differences documented.** No row replicates a Snowflake mechanism.
   The semantic-delta column is where the difference is named.

### Gov rule applied to every row (BLOCKING)

**Azure Government does not support Databricks SQL warehouses or Unity Catalog.** The research
output asserted Gov viability via Databricks in seven designs (query history, query details,
query profile, query insights, performance explorer, copy history, compute pools) and via
"Unity Catalog" in five more. Every one of those is **corrected here**: in the four sovereign
columns the mechanism is Synapse SQL / Azure SQL / ADX / Synapse Spark, and where a catalog is
required it is **self-hosted OSS Unity Catalog + the Iceberg REST catalog on Container Apps or
AKS** — which Loom already runs — never Azure Databricks UC.
