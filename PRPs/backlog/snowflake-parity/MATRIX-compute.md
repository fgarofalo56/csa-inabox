# Snowflake → CSA Loom capability parity matrix — **Compute & warehouses** (`compute`)

**Domain owner:** compute lane · **Written:** 2026-08-24 · **Verified against:** `9a888b58d6`

## Binding posture (operator, 2026-08-24 — settled, do not re-litigate)

1. **MIGRATION-FIRST.** Loom is the destination. The Snowflake MCP connector exists to read an
   existing account and extract data + definitions. Interop is the means, not the end state.
   The coexistence recommendation from research is **OVERRULED** — sequencing in this matrix
   assumes customers move *off* Snowflake.
2. **TRANSPILER NOW, WIRE-COMPATIBLE LATER.** An offline converter (Snowflake SQL, dbt projects,
   DDL, stored procs → Loom engines) ships first. A Snowflake-wire-compatible endpoint is a later
   wave. Rows below that assume a Loom-native surface (e.g. `LOOM_USAGE` views, `loom warehouse`
   CLI) are correct for wave 1; the wire-compatible spelling of the same thing is wave N.
3. **OUTCOME PARITY, DIFFERENCES DOCUMENTED.** Match what a user can exercise and observe, using
   the best Azure/OSS mechanism underneath. Mechanism parity (micro-partition pruning, Fail-safe,
   Snowgrid internals) was **REJECTED**. The `Semantic delta` column is therefore the contractual
   column of this document, not a footnote.
